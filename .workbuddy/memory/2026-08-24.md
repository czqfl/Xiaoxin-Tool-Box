## 截图呼出慢 + 拖动选区不跟手：热路径下沉原生层（未提交，待实测）
- 主人反馈：呼出截图要等一小会儿、左键拖选区不跟手；Snipaste 几乎零延迟。
  怀疑没用底层 API，要求参考别人的写法。上次会话中断，本次继续。
- 根因（两条热路径都卡在 webview）：
  1. 呼出：冻结帧写入后还要等「事件→JS 拉几何→React 渲染→双 rAF→IPC
     shot_ready」整条链路才亮窗，白付几十到一百多毫秒；
  2. 拖动：选区边框/压暗在 WebView2 里画，鼠标事件→rAF→光栅化→合成器
     天生落后真实光标 1~3 帧（60Hz 下 16~50ms）。此前 SVG→canvas、去
     desynchronized、事件内直绘、rAF 合并都试过，天花板就是合成器排队。
     Snipaste 是原生 GDI 直绘：光标移动→像素上屏只隔一次 DWM 合成。
- 改造一【原生即时亮窗】(screenshot.rs)：
  - 冻结层贴出的就是呼出瞬间真实屏幕像素，直接 show 无任何跳变——
    新增 native_show_overlay：统一写帧闭包与 create_overlays 自愈路径
    写完帧即亮窗+抢焦点（force_foreground_robust），只给前端留 ~24ms
    宽限清上一会话残留 DOM（OVERLAY_READY 先置位则仍走老次序）。
  - shot_ready 变幂等兜底；预热窗 SHOOTING=false 时入空不误显。
- 改造二【原生拖拽层】(screenshot.rs + ScreenshotOverlay.tsx)：
  - Rust：DRAG_PARAMS/DRAG_ACTIVE 静态态 + drag_updater 线程 ~1ms 轮询
    GetCursorPos → 按模式算矩形（框选 anchor 归一化 / 缩放对边锚点）
    → composite_drag 直接写冻结层 DIB（压暗行 memcpy 自预构建的 50%
    DIM_CACHE、镂空行 memcpy 原帧、边框/手柄 span 填色）→ InvalidateRect。
    全程零逐像素混合运算，单帧成本≈几次大 memcpy。
  - 前端只在【首次移动】发 shot_drag_begin（登记锚点/手柄/主题色/DPI 比）、
    【松手】发 shot_drag_end；拖动过程零 IPC。nativeDrag 期间 webview 选区
    画布清空保持全透明让位（paintSelCanvas 头部守卫），松手 handover：
    先解标志→webview 按最终矩形重画→再通知 Rust 还原原帧，同帧落屏无闪烁。
  - 绘制目标选冻结层（webview 之下）而非新窗口：免 z 序/输入穿透问题。
- 并发安全：新增 FREEZE_BITS_LOCK 统一锁序【先 BITS 后 FREEZES】——
  WM_PAINT BitBlt / 会话换帧 / 拖拽直写 / freezes_drop_all 四方互斥，
  防 DIB 写读撕裂与 use-after-free；hide_all 收场时 drag_stop 还原帧。
- 配套：loadSession 兜底停更+还原、root[data-resetting] 隐藏旧浮层 DOM
  （呼出竞态窗口期防旧工具栏闪现，循环结束/异常路径都会解除）；
  tauri.ts 新增 shotDragBegin/shotDragEnd 包装；lib.rs 注册两命令。
- 已知取舍：拖拽中标注/放大镜仍在 webview 层（亮度不随原生压暗变化，
  松手恢复一致）；缩放最小尺寸钳制只在 webview 最终提交时生效。
- 验证：cargo check + tsc --noEmit 通过。重启 `npm run dev:app` 后实测：
  ①呼出是否即刻出现（不再等一拍）；②拖动边框是否逐像素跟手。
- 注意：本文件与 ScreenshotOverlay.tsx/screenshot.css 同时有另一批
