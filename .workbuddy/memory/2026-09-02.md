## 贴图(pin)拖动卡顿排查与修复（本轮）

- **主人现象**：① 贴图刚贴上立刻拖动卡顿；② 有时贴了很久也明显卡。
  主人猜测「创建元素慢，能否预建备用元素 + 空闲补充」。
- **事实澄清**：备用池机制【早已存在且工作正常】——pin.rs 有
  `STANDBY_COUNT=2` 张屏幕外(-32000)**可见**待命窗（合成器预热，移动即显示）、
  `pin_busy/INTERACTING + wait_idle()` 空闲补建。diag.log 实测贴图链路

  用户起手拖动直接撞上 → "刚贴上立刻拖卡一下"。
  （对比：attach_to_staging 的补建有 wait_idle(8000)，两处不一致 = 遗留遗漏）

### 续：找到「松手后卡一下」的确凿根因（e2bc068）

- **`pin_update` 无条件动窗口**：`w.set_position(win_pos(x,y))` +
  `w.set_size(win_size(w,h))` 每次都执行。而前端 `persistNowRef` 在
  **每次拖动松手（onMoved 防抖 400ms）+ 每次 mouseup 监听** 都会用当前几何
  回写持久化 → 几何一字未变却照样 set_size → 触发 WM_SIZE → 整页重新布局
  + 重新光栅化（4K 贴图可达数百毫秒）= 主人说的"贴了很久也卡、很明显"。
- 修复：改【变化才动】——先 `outer_position()/inner_size()` 比对目标几何，
  无变化则一次窗口操作都不做；`set_ignore_cursor_events` 同样只在
  click_through 真正翻转时才调（改窗口样式会触发重绘）。
- **通用教训**：任何「用当前值回写持久化」的路径都不要顺手重设窗口几何，
  必须先比对——这类"幂等但昂贵"的调用正是隐性卡顿的高发区。
### 续：找到「松手后卡一下」的确凿根因（e2bc068）

- **`pin_update` 无条件动窗口**：`w.set_position(win_pos(x,y))` +
  `w.set_size(win_size(w,h))` 每次都执行。而前端 `persistNowRef` 在
  **每次拖动松手（onMoved 防抖 400ms）+ 每次 mouseup 监听** 都会用当前几何
  回写持久化 → 几何一字未变却照样 set_size → 触发 WM_SIZE → 整页重新布局
  + 重新光栅化（4K 贴图可达数百毫秒）= 主人说的"贴了很久也卡、很明显"。
- 修复：改【变化才动】——先 `outer_position()/inner_size()` 比对目标几何，
  无变化则一次窗口操作都不做；`set_ignore_cursor_events` 同样只在
  click_through 真正翻转时才调（改窗口样式会触发重绘）。
- **通用教训**：任何「用当前值回写持久化」的路径都不要顺手重设窗口几何，
  必须先比对——这类"幂等但昂贵"的调用正是隐性卡顿的高发区。

### 续：贴图拖动 200~800ms 单帧冻结 —— wait_idle 缺系统输入判定（真根因）

- **证据**：新写 scripts/pin-drag-stats.py 解析 diag.log 的 `[pin] drag Nf avg=.. p95=.. max=..`
  埋点，跑出 9 条记录：avg 只有 8~16ms（说明拖动本身很流畅），但 **max 平均 251ms、
  最差 816.8ms，6/9 次掉帧**。=> 不是持续卡顿，是【单次冻结】，且冻结与拖动起手高度相关。
- **根因**：补建待命窗前的 `wait_idle()` 只查前端上报的 `INTERACTING` 标记。
  补建线程 250ms 轮询时，用户常常【还没按下鼠标】-> 判定空闲 -> 开始建窗；
  WebView2 建窗 + 加载整个前端应用是**主线程数百毫秒且不可中断**的重活，
  用户恰恰在这段窗口里起手拖动 -> 单帧被拉到 200~800ms。
  （前端标记只能覆盖「已经按下之后」，覆盖不了「按下之前的意图」。）
- **修复**：`wait_idle` 改双重条件 —— ① INTERACTING 为假 且 ② 系统级输入静止
  >= 350ms。新增 `last_input_idle_ms()`（Windows 走 GetLastInputInfo + GetTickCount，
  覆盖本进程之外的全局输入；非 Windows 返回 u32::MAX 视为空闲），常量
  `INPUT_IDLE_MS = 350`，探测间隔 250ms -> 100ms。
- 同时把 `attach_to_staging` / `pin_ready` 两处 `wait_idle(8000)` 放宽到
  `wait_idle(30_000)`：实测一次拖动可长达十几秒，8s 上限会超时硬建窗，
  等于把保护作废。超时兜底仍保留（30s 后无条件建），避免用户一直动导致待命池长期空缺。
- **通用教训**：判断「用户现在忙不忙」，**进程内标记不够，必须叠加系统级
  输入空闲（GetLastInputInfo）**。标记只能反映已经开始的交互，系统输入时间戳
  才能覆盖「即将发生的交互」。凡是要在空闲时执行的不可中断重活（建窗、大 I/O、
  重编译），都应走这套双重门控。

### 续：贴图 OCR 弹窗翻译后没变大 + 翻译失败行不显（commit 151b00a）

**问题 ①：贴图 OCR 弹窗（独立 pin-ocr 窗）翻译后没自动变宽**

- 截图弹窗在同 WebView 内只切 CSS 就自动变大；贴图弹窗是独立 WebView 窗口，
  CSS 宽度变化不会自动同步到 OS 窗口尺寸。
- 必须由 useLayoutEffect 重新量尺寸 + setSize 才能让 OS 窗口真正变宽。
- 真根因：早返回检查只比较 mh，**宽度变化但 mh 未变时漏掉 setSize**，
  看起来窗口纹丝不动。
- 修复：
  - 加 PANEL_W_TRANS = 560 常量；transMode（trans 非空 || translating）
    时 inline style width 切 300 → 560，与截图弹窗的 320 → 560 对齐
  - useLayoutEffect 加 lastWRef 缓存上次窗口宽；早返回检查纳入 mw

**问题 ②：翻译后「原文 == 译文」看起来都是失败——两种本质不同的情形混在一起**

- ① 服务商原样返回：纯数字 / 标准号无可译内容 → has_cjk=false → target=zh，
  API 没东西可译返回 src，pr.ok=true。**这是 API 正常行为**。
- ② API 调用失败：网络 / 配额 / 行数超出 LINE_BLOCK_BUDGET(24) → 块请求折叠
  退回 per-line 仍超时 → pr.ok=false 回退 src。
- 原 .ocr-pfail 把译文列压暗到 0.42 透明度，差异太弱不易察觉，主人看不出
  哪些是真的失败哪些是「本来就没什么可译的」。
- 修复：失败行加 .ocr-pfail-tag 内联红色「未译」标签，仅在 !ok 时挂载，
  让两种情况视觉上一眼可辨。

**通用教训：**
- 独立 WebView 窗口的尺寸同步 = 量 DOM + setSize，**不能依赖 CSS 切宽**；
- 「幂等但昂贵」的早返回检查要覆盖所有可能变化的维度（这次只查了高度漏了宽度）；
- 状态布尔（ok=true/false）要在 UI 上有明确视觉表达，仅靠透明度差异不够；
  服务商返回原值和调用失败在数据层是两种状态，UI 必须能区分。

## 全局快捷键在 Electron/Chromium 系应用内失效（裸功能键走低级钩子，本次）

- **主人现象**：`shortcuts.screenshot = 'F1'` 在 WorkBuddy / VS Code 这类 Electron 应用里
  完全没反应（尤其截图），但在其他应用里正常。diag.log 铁证：在 WorkBuddy 按 F1
  无任何日志，其他应用里 `[shortcut] pressed F1 → screenshot triggered` 正常。
- **真根因**：`F1` 是裸功能键。原 `is_hook_combo` 只认 `SUPER`（Win+）和 `ALT`（Alt+）
  组合，裸键走 Tauri `global_shortcut`（底层 RegisterHotKey，靠系统发 `WM_HOTKEY`）。
  而 Electron/Chromium 应用在自身消息循环里**自行消费 F 键、不交给 DefWindowProc**，
  `WM_HOTKEY` 根本不生成 → RegisterHotKey 在这些应用里失效。
  （对比：WH_KEYBOARD_LL 低级钩子在事件到达任何应用之前就接管，天然免疫。）
- **修复**（keyhook.rs + shortcut.rs）：
  - `HookMode` 枚举（`Win`/`Alt`/`Bare`）替代原 `is_alt: bool`；新增 13 个
    `*_BARE_VK` 槽位（仅 F1~F12）。
  - `hook_proc` 加**裸功能键分支**：要求 `!win_held && !alt_held && !CTRL_HELD &&
    !SHIFT_HELD`（所有修饰键都未按住）才拦截，命中即吞键 post 对应 Action。
  - `is_hook_combo` 纳入 `mods 为空 && is_function_key(key)`；`register_combo`
    对 Alt **和** Bare 都额外 `global_shortcut().register` 做兜底。
  - `unregister_all_runtime` 清三套槽位；`shortcut_test` 对裸功能键也走真注册检测占用。
  - `hook_vk` 报错文案改为「钩子接管的热键仅支持字母、数字与 F 键」。
- **关键约束**：**仅功能键（F1~F12）可裸键**——裸字母/数字键会致用户打字打不出字符，
  绝对禁止路由到钩子吞键；裸键分支必须强校验 `is_function_key` 且所有修饰键未按住。
- 验证：`cargo check --message-format short` 无警告。改 Rust 需重编译，主人需重新
  `tauri dev` 后在 WorkBuddy 内按 F1 验证（diag.log 应出现 `[keyhook] bare hotkey
  matched vk=0x70`）。
