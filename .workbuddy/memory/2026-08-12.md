## 剪贴板 FIFO/LIFO 拖拽排序释放闪烁修复
- 现象：顺序模式拖动排序松手时列表"闪一下"（先跳回原位、再跳到新位）。
- 根因：`finishDrag` 松手时立即 `setVisualOrder(null)`——displayList 从拖拽中的视觉顺序
  瞬间跳回按 created_at 的旧队列顺序（被拖条目跳回原位置），随后 `reorderQueueEntry`
  调后端 `clipboard_reorder` 改 created_at → EVT_CHANGED → refresh → queue 重算成新顺序
  （又跳一次）。两次跳变合成"闪一下"。
- 修复：松手时**保持视觉顺序**，先 `reorderQueueEntry(id, overId).then(() => refresh())`
  等后端重排完成、列表刷新（此时 queue 顺序已等于视觉顺序），再清 visualOrder/dragState，
  顺序无跳变即无闪烁。后端 clipboard_reorder 排序逻辑与前端 applyVisualOrder 一致，
  保证了"新队列顺序 == 视觉顺序"。
- 纯前端改动（ClipboardPanel.tsx finishDrag），npm run build 通过。

## VS Code 打开实际启动 Qoder（probe_vscode 顺序修复）
- 现象：右键「用编辑器打开 → VS Code」实际打开的是 Qoder CN。
- 根因：`probe_vscode` 探测顺序是 configured → **PATH code 命令** → 标准安装路径。用户机器上

  （盘根），但探测在第 2 步就返回了 Qoder，没走到盘根扫描。

- 教训：PATH 中的 `code` 命令可能被 VS Code 系 IDE（Qoder/Windsurf/Cursor）抢占注册；
  探测编辑器优先走安装路径而非 PATH 命令。

## ⚠️ 翻译面板按"正常面板"标准架构重建（本日最终修复，推翻前几轮部分结论）
用户多次反馈"改了没用"，要求按 folder/credential/clipboard 面板的架构重做。
读透面板标准行为（usePanelCommon）后定位到**两个此前漏掉的真因**：

**真因 1（识别不到选中内容）**：TranslatePopup 的 useEffect 在挂载时调用了
`getCurrentWindow().setFocus()`——窗口一显示，前端立刻把**弹窗**抢成前台。而此时
后端还在做"模拟 Ctrl+C 复制"（复制发生在 show 之前、async 任务里），SendInput 的
Ctrl+C 于是发给了**本工具自身**而非源应用 → 永远复制不到选中文字。
→ 正常面板（usePanelCommon）**从不在挂载时抢焦点**，只靠后端 force_foreground（热键后
  同步即时激活）+ 前端"鼠标移入/点击即聚焦"兜底。翻译面板独有的是 bug 根源。

**真因 2（无法拖动/点击/Esc）**：trigger_selection_translate 是 async 任务，要先
"存剪贴板→等修饰键释放(≤600ms)→3~4次模拟Ctrl+C(各150ms)→翻译API"才激活窗口，
**晚于用户按键约 200ms 的前台锁输入窗口**，普通 SetForegroundWindow 被系统拒绝，
窗口显示在最前却无焦点 → 交互全失效。面板在热键后同步即时激活（落在输入窗口内）所以正常。

**重建要点（与面板对齐）**：
- 后端拆分 show_popup → reveal_popup（仅 show，不抢焦点，立即给视觉反馈）+
  focus_popup（复制/翻译完成后调用）。reveal_popup 先显示弹窗并 emit `translate://start`。
- 复制期间用 keyhook::foreground_hwnd() 记录源应用、ensure_foreground() 锁住其前台，
  send_ctrl_c 前 wait_modifiers_released() 防误触 QQ 截图。
- focus_popup 用新增 acrylic::force_foreground_robust（先 SetForegroundWindow，失败再
  AttachThreadInput 附加到前台线程后抢前台，**不受前台锁超时限制**）。150ms 后台线程再补一次。
- 前端：移除挂载时 setFocus；失焦隐藏 + 鼠标移入/点击聚焦（对齐 usePanelCommon），
  但**复制/翻译进行中(loading)绝不抢焦点**（用 loadingRef 守卫），避免再次抢走源应用焦点。
  加"翻译中…"加载态（translate://start → loading，applyResult → 解除）。
- 后端加 storage::diag_write 写 data/diag.log（记录复制逐次尝试的 prev/cur 长度与是否变化、
  selected 长度），便于复现失败时定位是复制失败还是激活失败。
- 新增/改动：storage.rs(diag_write)、acrylic.rs(force_foreground_robust)、
  keyhook.rs(foreground_hwnd/ensure_foreground)、translate.rs(重建)、TranslatePopup.tsx(对齐面板)。
- cargo build + npm run build 均通过。
- **教训（推翻前几轮）**：① 调出即焦点抢走 ≠ 复制失败的根因是"激活时机"，而是
  "前端挂载即 setFocus 抢走源应用焦点"；② 单纯对齐面板调用顺序不够，因为翻译必须
  "先复制后激活"导致激活必然落在前台锁窗口之外，必须用 AttachThreadInput 可靠置前。

## ⚠️ 翻译面板仍"选中内容不出现 / 拖不动 / 关不掉"——最终定位（关键演进）
用户再次反馈"右上角关闭不生效、依旧无法拖动、选中内容没出现在面板上"，前一轮重建仍无效。
读 data/diag.log 拿到决定性证据：每次触发 `cur_clip_len=14 changed=false`（4 次全一样）、
`selected_len=0`；但 `close click` 有记录（点击确实进了 webview）→ 不是前端没挂载/没加载。

**铁证指向 Bug A 的真正根因（前一轮也没修对）**：
前一轮"重建"里 `src_hwnd = keyhook::foreground_hwnd()` 是写在 **async 任务里、reveal_popup() 之后**。
而 `reveal_popup` 的 `w.show()`（SW_SHOWNORMAL）会把**本工具窗口激活为前台**——于是 async 任务
里再取前台拿到的已经是**本工具自身**，`ensure_foreground(本工具窗口)` 锁住的也是自己，
`send_ctrl_c` 的 Ctrl+C 发给自身空 textarea → 剪贴板不变 → `selected_len=0`。
（diag 里 `cur_clip_len=14` 就是用户开机时已在剪贴板里的旧内容，复制从未改变它。）

**修复（两步，缺一不可）**：
1. **在 show() 之前、且在按键瞬间**捕获真实源窗口：低级键盘钩子 `hook_proc` 的 keydown 分支
   （任何应用被抢焦点之前）记录 `LAST_FOREGROUND = GetForegroundWindow()`，暴露
   `source_hwnd_at_keydown()`。`trigger_selection_translate` 在 `reveal_popup` **之前**调用它
   （取不到再回退 `foreground_hwnd()`），存成 `usize`（HWND 非 Send，跨 spawn 线程需转成 usize 再重建）。
2. **复制期间用 AttachThreadInput 兜底锁源前台**：把 `ensure_foreground` 换成
   `set_source_foreground`（AttachThreadInput(本线程, 源线程) 后 SetForegroundWindow，再解除附加）。
   即使本工具已因 show() 抢到前台，也能把源应用拉回前台 → SendInput 的 Ctrl+C 命中源应用。

**Bug B（拖不动/关不掉）是 Bug A 的连带**：复制恒失败 → 弹窗长期停在 loading，且此前
`focus_popup` 的 `force_foreground_robust` 虽能置前，但源应用前台状态被复制循环反复拉扯，
交互不稳。复制修对后，复制/翻译完成 `focus_popup` 用 `force_foreground_robust` 可靠激活，
弹窗获得真实焦点 → × 关闭 / 头部 data-tauri-drag-region 拖动 / Esc 全部恢复（与面板一致）。

**改动文件**：keyhook.rs（LAST_FOREGROUND 静态 + source_hwnd_at_keydown、set_source_foreground、
  hook_proc keydown 记录前台）、translate.rs（show 前捕获 src_raw、循环用 set_source_foreground、
  加 src_hwnd 诊断日志）、acrylic.rs 已有 force_foreground_robust 复用。
**验证**：`cargo build` 通过。diagnostic 现记录 `src_hwnd=0x...`（应≠0 且≠本工具窗口）与
各 attempt 的 `changed=`；若 src_hwnd 正确且某次 changed=true → 选中内容会出现在面板。
**核心教训**：划词翻译"复制选中文本"的前提是**复制时源应用必须是前台**；窗口的 show() 会抢前台，
所以"源窗口句柄"必须在 show() 之前、最好按键瞬间（低级钩子）捕获，复制期用 AttachThreadInput
可靠回拉源前台——这是与"只显示已有内容"的普通面板最本质的区别，也是多轮失败的总根。

## 翻译面板"一点击就消失"（DOM blur 误伤）

**现象**：划词弹出翻译面板后，鼠标一点击面板（尤其头部）整窗就隐藏。

**根因**：`TranslatePopup.tsx` 用 `window.addEventListener("blur", () => hideCurrentWindow())`
做"失焦隐藏"。但 `data-tauri-drag-region` 头部在有 `allow-start-dragging` 权限后会触发**原生窗口拖动**，
原生拖动时 WebView2 会瞬时失焦、`blur` 即触发 → 误隐藏。这是上一轮"加头部拖动 + 补 translate-popup
拖动权限 + 对齐面板的 blur→hide"三件事叠加出来的回归。

**修复**：把隐藏条件从 DOM `window blur` 改为窗口级 `getCurrentWindow().onFocusChanged(({focused}) => ...)`
且仅当 `prev && !focused`（焦点真正离开本窗口，点到别的程序）才隐藏。窗口级焦点在内部点击/原生拖动时
**不变**，故不会误触发；`prev` 守卫还能避免 reveal_popup 以未聚焦方式显示时立即被藏。

**验证**：`npx tsc --noEmit` exit 0。GUI 真机点击/拖动需本机 `npm run tauri dev` 自测（沙箱无桌面）。
**核心教训**：Tauri 带 drag-region 的悬浮窗，**不要用 DOM `window blur` 做关闭**，必须用窗口级
`onFocusChanged(focused=false)`——原生拖动会让 webview 瞬时失焦触发 blur，会把面板自己关掉。

## 翻译面板填充"历史复制内容" + 点头部仍关闭（set_source_foreground bug）

**现象（用户复测）**：① 面板里填的是旧剪贴板内容而非选中文本；② 点上方拖动区仍直接关闭。

**根因①（复制从未生效）**：diag 铁证——每次 `attempt 0..3: cur_clip_len=154 changed=false`、
`selected_len=0`。复制选中文本失败的真正原因在 `keyhook.rs::set_source_foreground`：它
`AttachThreadInput(cur, src_thread, ...)` 把本线程**附加到源线程**，再 `SetForegroundWindow(src)`。
但突破前台锁的标准做法是**附加到"当前前台线程"**（`force_foreground_robust` 的正确逻辑），附加到
源线程无法从真正的前台窗口抢回焦点 → `SetForegroundWindow` 被前台锁拒绝 → 源应用没被拉回前台 →
`SendInput` 的 Ctrl+C 发错地方 → 剪贴板不变 → 选中文本永远为空 → 面板只能显示挂载兜底拉出的旧结果。

**修复①**：`set_source_foreground` 改为与 `force_foreground_robust` 一致——先直接 `SetForegroundWindow`，
失败则**附加到当前前台线程**再抢前台。复制步骤改调它后，源应用能可靠回前台，Ctrl+C 命中源应用。

**根因②（仍误关）**：上一轮的 `onFocusChanged(focused=false)` 仍会在两类瞬时失焦上误关：
- 点/拖 `data-tauri-drag-region` 头部触发原生拖动 → WebView2 瞬时失焦；
- 上一次已聚焦、再次呼出时 `reveal_popup` 让窗口短暂失焦（onFocusChanged 由 true→false）。

**修复②**：在 `TranslatePopup.tsx` 加两道守卫——`dragGuardRef`（在 drag-region 上 mousedown/移入
即置位，window mouseup 后 250ms 解除；期间失焦不关、也不抢焦点）+ `lastStartAt`（呼出后 1s 内忽略失焦隐藏）。
`prev` 守卫保留（reveal 以未聚焦显示不初关）。

**验证**：`npx tsc --noEmit` exit 0；`cargo check --lib` exit 0。
**核心教训**：划词翻译复制阶段"拉回源前台"必须用"附加当前前台线程"的 AttachThreadInput，
**绝不能附加源线程**——这会让 Ctrl+C 复制永远失败（与"复制命中自身"同源不同表述）。

## 复制选中文本偶发失败（用户复测：偶尔复制不到）
- 根因是**时序竞态**：原流程每次只 `set_source_foreground` 一次 + 等 150ms 读一次。但 `reveal_popup` 的
  `show()` 把工具窗置为前台、与复制任务抢焦点；部分应用（浏览器/Electron/Office）复制异步、或焦点尚未沉降，
  单次 Ctrl+C 吃不到 → 偶发 `changed=false`。
- 加固（translate.rs 复制循环）：
  1) 每次 attempt 拉回源前台后**轮询 `foreground_hwnd()==src`**（最多 5×40ms）确认源真正前台，否则补拉；
  2) 注入 Ctrl+C 前加 **60ms 焦点沉降延时**；
  3) 读取改**两档（110ms / 再 110ms）**各读一次接受任意变化，应对异步复制；
  4) 重试 4→5 次。
- 方向逻辑 #2 复核：`target_for_text` 已是 中文→en / 否则→zh（4 个单测通过）。用户看到的"方向偶尔错"是
  复制失败时拿到旧/错文本导致，复制稳了方向即稳定。
- `cargo test --lib` 6/6 通过（含 4 个方向单测）。

## 复制仍偶发失败 → 根因是弹窗 show() 抢前台（焦点竞态，非时序）
- 上一轮加固（轮询前台/沉降/两档读/重试）后仍"偶尔复制不到"，说明不是时序而是**结构性竞态**：
  `reveal_popup` 用 `w.show()` 把翻译弹窗激活为前台，与复制任务"拉源应用前台"互相抢焦点
  （show() 的激活是异步落到 OS 消息循环的，可能在 set_source_foreground 之后才生效）。
- 根因级修复：`reveal_popup` 改为 **`ShowWindow(hwnd, SW_SHOWNA)` 仅显示不激活**（取原生 HWND 用
  `raw_window_handle`：HWND(h.hwnd.get())）；源应用全程保持前台 → 复制天然可靠。弹窗激活统一延后到
  复制/翻译完成后的 `focus_popup`（`force_foreground_robust` + set_focus）。
- 复制回路再补一道 `WM_COPY`：`send_wm_copy(src)` 用 `GetGUIThreadInfo` 取源线程焦点控件并 `SendMessageW(WM_COPY)`，
  原生编辑控件比模拟 Ctrl+C 更稳；浏览器等仍靠 Ctrl+C。读取档位改为 100/200/350ms 三档轮询。
- `cargo test --lib` 6/6 通过。本版后复制应接近 100% 成功（若仍偶发，多半是源应用以管理员运行→需本工具也管理员）。

## 【最终定论】划词翻译顺序重构：先复制 → 后显示（推翻此前全部焦点技巧）
用户一句话点醒："不就是先复制，然后把复制内容放面板，翻译，最后把剪贴板那条删掉吗？"——**是的，
之前所有麻烦都来自把顺序搞反了**。SW_SHOWNA 虽让复制不再被抢焦点，但面板全程拿不到焦点，
于是"关不掉/拖不动"复发。正确架构（`trigger_selection_translate`，勿再倒回去）：

1. **先复制**：热键触发瞬间源应用天然在前台 → 此阶段**绝不显示/激活任何窗口** → Ctrl+C 必然发到源应用。
   不再需要任何焦点争夺技巧（`set_source_foreground` 仅在"上一次面板还开着"时用一次，确定性无竞态）。
   进入前先 `w.hide()` 已可见的面板，并过滤掉"keydown 源句柄 == 面板自身"的情况。
2. **还原剪贴板**：写回原内容（等价于删掉我们复制的那条），`SUPPRESS_WATCH` 置位不进历史。
3. **再显示并激活面板**：`show()` + `force_foreground_robust()` + `set_focus()` → 拿到**真实焦点**
   → 能拖动 / 点 × / 按 Esc；同时用 `translate://start { text }` 立刻带出原文。
4. **最后翻译**：异步 HTTP，译文到达后 emit 填充。

配套关键修复：
- **复制成功判据改用 `GetClipboardSequenceNumber()`**（新增 `keyhook::clipboard_seq()`）。
  旧判据"剪贴板内容是否变化"在**选中文字恰好与剪贴板已有内容相同**时会误判为失败——这是
  "偶尔复制不到"的一类隐藏成因。序列号任意进程写入即自增，是唯一可靠信号。
  需在 Cargo.toml windows features 里有 `Win32_System_DataExchange`（本项目已有）。
- 复制阶段放 `std::thread::spawn`（同步 Win32 时序 + sleep），翻译才交 `tauri::async_runtime::spawn`。
- store 先写 `translation: ""` 占位（原文已就位、译文在路上），前端 `applyResult` 遇空 translation
  保持 loading，解决"面板首次创建错过 start 事件"时原文不显示的问题。
- 前端 `onMouseDown` 里**拖动守卫必须在任何 return 之前置位**：原先 `if (loadingRef.current) return;`
  排在守卫之前，导致"翻译中"点头部守卫失效，翻译一旦超过 lastStartAt(1s) 窗口就会误关面板。
- 顺序倒过来后，"loading 期间不抢焦点"这条限制**已无意义并已删除**（复制早于面板显示完成）。
- `reveal_popup`/`focus_popup` 合并为单一 `show_popup_activated(app, text)`。

验证：`cargo build --lib` 零告警、`cargo test --lib` 6/6、`tsc --noEmit` exit 0、`vite build` 成功。

**核心教训**：涉及"从别的应用取数据 + 显示自己的窗口"的流程，**先取数据、后显示窗口**是唯一
不需要与 OS 焦点机制搏斗的架构。一旦顺序反了，后续所有 AttachThreadInput / SW_SHOWNA /
前台锁技巧都只是给错误架构打补丁，且必然在别处冒出新症状（此案例前后反复 5 轮才定位）。

## 设置面板打不开（新触发路径：托盘左键 + 全部入口永久失效，根因修复）
- 现象（用户精确复述）：打开其他面板时，点托盘图标左键打开设置 → 打不开，之后托盘右键「打开设置」也打不开（所有入口失效，本次运行内不可恢复）。

- 修复（commit bcc2f48）：
  1. **根治**：tray.rs 新增 `protect_settings_window`——拦截设置窗口 `CloseRequested`，`prevent_close` + `hide`（关闭=隐藏，不再销毁）；lib.rs setup 挂载。
  2. **兜底**：`ensure_settings_window`——窗口已销毁时按 tauri.conf.json 配置自动重建（URL 跟随 dev_url/prod，重建后重新挂关闭拦截）；`toggle_settings_window`/`show_settings_window` 均走此路径，老版本残留的销毁态也能自愈。
  3. **自愈**：show 后检查 is_visible，极端态（最小化+隐藏）用 Win32 `ShowWindow(SW_SHOWNORMAL)` 强制激活显示。
  4. **前端**：SettingsApp 包 SettingsErrorBoundary（新文件 ErrorBoundary.tsx），渲染崩溃白屏时 2.5s 自动 reload + 手动按钮。
  5. diag 日志：show_settings_window 记录 visible/focused 与重建事件（data/diag.log）。
- 验证：cargo check（0 警告）+ tsc + vite build 通过；已 commit 未 push。
- 经验：Tauri 2 中"窗口关闭=销毁"是打不开类问题的头号嫌疑；需要"关闭=隐藏"语义的窗口必须拦截 CloseRequested。show_settings_window 类函数应先保证窗口存在再隐藏其他窗口，避免"面板被收走+窗口不存在"双失败。

## Alt 组合热键全部失效——GetAsyncKeyState 陈旧状态误判（commit 157df95 + 2fcbb8e）
- 用户反馈：所有单功能键+字母（Alt+C/F/A/S）都无法触发。上一版把 Alt 匹配加了
  `!ctrl_held() && !shift_held()`（GetAsyncKeyState）条件——**GetAsyncKeyState 在钩子
  线程只在消息循环处理时刷新快照，用户之前按过 Ctrl（复制粘贴）的陈旧状态让
  !ctrl_held() 恒为 false → 所有纯 Alt 热键永久不匹配**。
- 修复：Alt 匹配只依赖 ALT_HELD（钩子自己维护，可靠），去掉 GetAsyncKeyState 判断；
  删除 shift_held。副作用：Alt+Ctrl+X 也会命中（若 X 是热键主键），可接受。
- 诊断：set_panel_hotkey 记录 "[keyhook] hotkey set: target alt= vk="；Alt 匹配命中
  记录 "[keyhook] alt hotkey matched vk="；配合已有的 "[keyhook] translate hotkey pressed"。
- 教训：**钩子线程里的 GetAsyncKeyState 不可靠（陈旧快照），判断修饰键状态必须
  用钩子自维护的静态变量（ALT_HELD/WIN_HELD）**。

## Alt 组合双保险方案（commit 0fd3906，最终方案）
- 用户多轮反馈：纯 Alt 组合（Alt+C/F/A/S）全部失效，而 RegisterHotKey 的组合（Ctrl+Alt+E）一直正常。keyhook 接管 Alt 的方案在用户机器上不可靠（ALT_HELD 未置位等未知原因，即使去掉 GetAsyncKeyState 条件仍失效）。
- **最终方案：Alt 组合【双保险】注册**——
  1. keyhook set_panel_hotkey（吞键防泄漏 + 触发）；
  2. **同时 RegisterHotKey 注册（兜底触发）**。
  互斥不冲突：钩子吞键→按键不达系统→RegisterHotKey 不触发；钩子放行→RegisterHotKey 触发。
  **无论钩子是否正常，Alt 组合必能呼出**。代价：钩子异常时兜底触发可能重新出现主键泄漏（VS Code 中文字被替换），但"能用"优先。
- unregister_combo 双注销；shortcut_test 对 Alt 组合用 RegisterHotKey 试注册检测真实冲突。
- 经验：**热键"必须能触发"优先于"防泄漏"**；把两种注册叠加成双保险，规避单一机制在特定机器上的不确定性。

## 修饰键键码终极根因（commit 0189f03）——Ctrl+V 顺序粘贴 & Alt 热键
