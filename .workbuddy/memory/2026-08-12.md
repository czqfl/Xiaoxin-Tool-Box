## 剪贴板 FIFO/LIFO 拖拽排序释放闪烁修复
- 现象：顺序模式拖动排序松手时列表"闪一下"（先跳回原位、再跳到新位）。
- 根因：`finishDrag` 松手时立即 `setVisualOrder(null)`——displayList 从拖拽中的视觉顺序
  瞬间跳回按 created_at 的旧队列顺序（被拖条目跳回原位置），随后 `reorderQueueEntry`
  调后端 `clipboard_reorder` 改 created_at → EVT_CHANGED → refresh → queue 重算成新顺序
  （又跳一次）。两次跳变合成"闪一下"。
- 修复：松手时**保持视觉顺序**，先 `reorderQueueEntry(id, overId).then(() => refresh())`
  等后端重排完成、列表刷新（此时 queue 顺序已等于视觉顺序），再清 visualOrder/dragState，
  顺序无跳变即无闪烁。后端 clipboard_reorder 排序逻辑与前端 applyVisualOrder 一致，
  保证了"新队列顺序 == 视觉顺序"。
- 纯前端改动（ClipboardPanel.tsx finishDrag），npm run build 通过。

## VS Code 打开实际启动 Qoder（probe_vscode 顺序修复）
- 现象：右键「用编辑器打开 → VS Code」实际打开的是 Qoder CN。
- 根因：`probe_vscode` 探测顺序是 configured → **PATH code 命令** → 标准安装路径。用户机器上
  `D:\QoderCN\bin\code.cmd` 在 PATH 里排在 `D:\Microsoft VS Code\bin\code.cmd` 前面（where code
  第一行是 Qoder），于是 code 命令被误判为 VS Code；真 VS Code 装在 `D:\Microsoft VS Code`
  （盘根），但探测在第 2 步就返回了 Qoder，没走到盘根扫描。
- 修复：探测顺序改为 configured → **标准安装 + 盘根/scoop**（真 VS Code Code.exe）→ PATH code
  （兜底，排除路径含 qoder/windsurf/cursor 的抢占项）→ 受限全盘扫描。
- 教训：PATH 中的 `code` 命令可能被 VS Code 系 IDE（Qoder/Windsurf/Cursor）抢占注册；
  探测编辑器优先走安装路径而非 PATH 命令。

## 翻译弹窗交互失效——真正根因（对比其他面板发现）
- 用户提示"看其他面板怎么做的"。对比发现关键差异：
  - 其他面板呼出：`acrylic::force_foreground`（SetWindowPos 无 SWP_NOACTIVATE → 激活窗口）

- 修复：show_popup 改回 `force_foreground`（与面板完全一致）；前端头部恢复

- 教训：**所有置顶面板/弹窗的呼出置前必须统一用 force_foreground（激活窗口），
  绝不能带 SWP_NOACTIVATE**；发现"某窗口交互全失效"时先对比正常窗口的呼出路径。

## ⚠️ 翻译面板按"正常面板"标准架构重建（本日最终修复，推翻前几轮部分结论）
用户多次反馈"改了没用"，要求按 folder/credential/clipboard 面板的架构重做。
读透面板标准行为（usePanelCommon）后定位到**两个此前漏掉的真因**：

**真因 1（识别不到选中内容）**：TranslatePopup 的 useEffect 在挂载时调用了
`getCurrentWindow().setFocus()`——窗口一显示，前端立刻把**弹窗**抢成前台。而此时
后端还在做"模拟 Ctrl+C 复制"（复制发生在 show 之前、async 任务里），SendInput 的
Ctrl+C 于是发给了**本工具自身**而非源应用 → 永远复制不到选中文字。
→ 正常面板（usePanelCommon）**从不在挂载时抢焦点**，只靠后端 force_foreground（热键后
  同步即时激活）+ 前端"鼠标移入/点击即聚焦"兜底。翻译面板独有的是 bug 根源。

**真因 2（无法拖动/点击/Esc）**：trigger_selection_translate 是 async 任务，要先
"存剪贴板→等修饰键释放(≤600ms)→3~4次模拟Ctrl+C(各150ms)→翻译API"才激活窗口，
**晚于用户按键约 200ms 的前台锁输入窗口**，普通 SetForegroundWindow 被系统拒绝，
窗口显示在最前却无焦点 → 交互全失效。面板在热键后同步即时激活（落在输入窗口内）所以正常。

**重建要点（与面板对齐）**：
- 后端拆分 show_popup → reveal_popup（仅 show，不抢焦点，立即给视觉反馈）+
  focus_popup（复制/翻译完成后调用）。reveal_popup 先显示弹窗并 emit `translate://start`。
- 复制期间用 keyhook::foreground_hwnd() 记录源应用、ensure_foreground() 锁住其前台，
  send_ctrl_c 前 wait_modifiers_released() 防误触 QQ 截图。
- focus_popup 用新增 acrylic::force_foreground_robust（先 SetForegroundWindow，失败再
  AttachThreadInput 附加到前台线程后抢前台，**不受前台锁超时限制**）。150ms 后台线程再补一次。
- 前端：移除挂载时 setFocus；失焦隐藏 + 鼠标移入/点击聚焦（对齐 usePanelCommon），
  但**复制/翻译进行中(loading)绝不抢焦点**（用 loadingRef 守卫），避免再次抢走源应用焦点。
  加"翻译中…"加载态（translate://start → loading，applyResult → 解除）。
- 后端加 storage::diag_write 写 data/diag.log（记录复制逐次尝试的 prev/cur 长度与是否变化、
  selected 长度），便于复现失败时定位是复制失败还是激活失败。
- 新增/改动：storage.rs(diag_write)、acrylic.rs(force_foreground_robust)、
  keyhook.rs(foreground_hwnd/ensure_foreground)、translate.rs(重建)、TranslatePopup.tsx(对齐面板)。
- cargo build + npm run build 均通过。
- **教训（推翻前几轮）**：① 调出即焦点抢走 ≠ 复制失败的根因是"激活时机"，而是
  "前端挂载即 setFocus 抢走源应用焦点"；② 单纯对齐面板调用顺序不够，因为翻译必须
  "先复制后激活"导致激活必然落在前台锁窗口之外，必须用 AttachThreadInput 可靠置前。
